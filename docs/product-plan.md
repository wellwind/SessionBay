# Session Bay 產品企劃

Session Bay 幫助開發者以專案為單位找回 AI 開發工作的脈絡，再透過內嵌 Terminal 接續執行。產品價值在於縮短「回到專案到能繼續工作」的距離。

預設「專案」首頁管理使用者明確選擇的工作目錄；獨立「所有目錄」頁保留全部 Session 相關目錄分組。兩頁都以卡片與側欄先選目錄，再搜尋與預覽該組歷史，讓工作清單精簡而完整歷史仍可到達。

## 產品定位

**以專案為中心的 AI 開發工作台，集中管理不同 Agent 的工作脈絡，讓開發者隨時接續開發。**

Session Bay 的名稱取工作階段停靠站的意象。對外說明可使用「找回脈絡，接著工作」作為暫定標語；標語尚未定稿。

## 使用者痛點

| 痛點 | 真實工作情境 | 對應價值 |
| --- | --- | --- |
| 工具分散 | 忘記某段討論是在 Codex 還是 Claude Code | 跨工具的統一清單與搜尋 |
| 專案關聯不清楚 | 找到對話後，仍不知道當時操作哪個目錄或 worktree | 保留原始工作目錄，以專案組織 Session |
| 導覽被暫存目錄淹沒 | Agent 曾在許多零散目錄工作，但只有少數是要持續經營的專案 | 所有目錄保留完整歷史分組，專案首頁由使用者選擇 |
| 工作恢復成本高 | 隔幾天回來，要找紀錄、回想進度、切目錄、重開工具 | 預覽最後進度，在正確環境恢復對話 |
| 執行環境零散 | 在 Agent 視窗、Shell、測試與服務日誌之間來回切換 | 同一工作區內使用分頁與分割面板 |
| 個人工作方式不同 | 字型、快捷鍵、版面與慣用 Shell 無法配合習慣 | 宣告式設定與可客製化工作區 |
| Agent 用量分散 | 不清楚各工具還有多少額度，或哪些專案與對話消耗最多 | 統一額度總覽與可追溯的 Project／Agent／Session 用量分析 |

這些痛點是根據目前需求提出的產品假設，尚未經訪談與使用數據驗證。

## 目標使用者

優先服務經常切換專案、同時使用多種 AI coding CLI 的個人開發者。他們已有自己的 Shell 與開發工具，希望保留既有習慣，同時改善歷史搜尋與工作接續。

次要使用者是同時管理多個 repository 或 worktree 的進階開發者。團隊共享、多人管理與企業治理屬於後續研究範圍。

## 主要使用情境

### 回到中斷的工作

使用者開啟 Session Bay，從專案首頁或所有目錄總覽選取目錄，找到前幾天的工作，透過搜尋與預覽確認對話，直接恢復對應 Agent Session。需要資訊不足時，能展開原始對話核對；值得持續工作的目錄可從預覽明確加入專案。

### Agent 工作與手動驗證並行

左側面板執行 Agent，右側面板執行測試、Git 指令或開發伺服器。兩個面板有各自的程序、輸入焦點與輸出，並共享使用者選定的專案工作區。

### 各工具保留慣用啟動方式

Codex、Claude Code、Grok Build 與 Antigravity CLI 可保存各自的啟動參數。使用者明確啟用危險模式後，不必每次在 Session Bay 重複確認；預設不加 bypass，啟動前顯示實際 argv 與風險。歷史支援按工具分開，Antigravity 目前只提供新工作及手動 ID 接續。

### 在專案內開始新任務

使用者選擇專案與 Agent，建立新的工作階段；需要自由操作時，直接開普通 Terminal。新對話在可確認來源關聯後納入該專案的紀錄。

沒有既有專案時，可以加入現有目錄，或在已存在的父目錄下建立單一新資料夾。移出專案只整理導覽，不刪除檔案與歷史；已開啟工作區保持可操作。

### 未來的跨 Agent 交接

使用者挑選對話內容、檔案與下一步，形成可預覽的交接內容，再交給另一個 Agent。這是後續功能，不能等同於完整搬移模型內部狀態。

### MVP 後的 Agent 用量瀏覽

使用者查看各 Agent／帳號的額度與重置時間，再依專案、工具或 Session 檢視 token 與有依據的費用。缺少事件歸屬或價格時明確顯示不完整，不把共享額度與訂閱月費當成可直接分攤的專案費用。使用者已指定整組功能在 MVP 後交付，詳見[用量規格](usage-spec.md)。

## 產品原則

- **專案由使用者選擇**：工作目錄是歷史分組基礎，側欄只放明確加入的專案；Agent 是工作區內的工具。
- **歷史入口完整**：所有目錄的分組不受專案加入、移出或釘選影響；選組後再查看對話。
- **能力入口一致**：四 Agent 的設定卡片固定可見，啟動與歷史能力分開說明，不以是否曾啟動決定能否設定來源。
- **接續優先**：清單、搜尋與預覽都服務於重新開始工作。
- **本機優先**：基本索引、搜尋與設定不需要 Session Bay 雲端帳號。
- **沿用既有工具**：以原 Agent 的正式啟動與恢復能力執行工作。
- **狀態可信**：有歷史、有執行檔、程序活著、任務完成，是不同狀態。
- **普通 Terminal 完整可用**：Shell 與 Agent 可以同時存在，也能獨立使用。
- **客製化有一致入口**：主題、快捷鍵、布局與 Profiles 使用可驗證的設定模型。

## 第一版的價值邊界

第一版優先完成可重複使用的工作恢復流程，以及普通 Terminal 與 Agent 並排操作。完整終端相容性是長期方向，首版以明確的相容性清單驗證，不以「支援所有協定」作承諾。

首版不處理雲端限定歷史、已刪除紀錄復原、跨機同步、多 Agent 自動派工或完整 IDE。UI 重開時恢復布局，和保留持續執行的程序也分開交付。

## 驗證計畫

| 假設 | 驗證方式 | 判讀重點 |
| --- | --- | --- |
| 跨工具找歷史是反覆出現的痛點 | 訪談與觀察近期實際工作恢復流程 | 發生頻率、耗時、目前替代方法 |
| 依專案分組比依 Agent 分組直覺 | 比較兩種原型完成同一搜尋任務 | 找錯率、完成時間、使用者信心 |
| 最近對話預覽足以協助接續 | 使用真實或經同意去識別的歷史做任務測試 | 是否仍需大量翻閱正文 |
| 內嵌 Terminal 能成為日常工作場所 | 小規模試用，觀察恢復後是否持續在應用內操作 | 相容性阻礙、切回其他 Terminal 的原因 |

## 成效指標

優先觀察「找到正確 Session 的時間」、「從選擇專案到開始接續的時間」、「恢復成功率」與「在錯誤目錄啟動的次數」。次要觀察搜尋無結果率、索引錯誤率與工作區持續使用情況。

初期由本機診斷或使用者同意的測試蒐集數據。正式產品若加入遙測，需另定資料範圍與啟用方式；對話正文不應預設成為產品分析資料。
